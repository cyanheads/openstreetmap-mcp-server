# 0.3.0 — 2026-07-26

## Changed

- **`openstreetmap_geocode` → `openstreetmap_search_places`, `openstreetmap_reverse` → `openstreetmap_reverse_geocode`, `openstreetmap_lookup` → `openstreetmap_lookup_objects`** — the Nominatim-facing tools now follow the same explicit `openstreetmap_<verb>_<object>` pattern as the Overpass tools. Inputs, outputs, errors, and runtime behavior are unchanged; only the tool names and their internal cross-references moved. Overpass tool names (`openstreetmap_query_nearby`, `openstreetmap_query_bbox`, `openstreetmap_query_raw`) are unaffected. ([#30](https://github.com/cyanheads/openstreetmap-mcp-server/issues/30))
- **`openstreetmap_lookup_objects`'s `osm_ids` is array-only** — the single-string branch is gone; a bare string or a JSON-stringified array now fails at the Zod boundary with `expected array, received string` instead of reaching the handler and being misdiagnosed as one malformed ID. A single lookup is now `["N240109189"]`, not `"N240109189"`. The `invalid_id_format` recovery hint now also covers a nested list crammed into one array element. ([#29](https://github.com/cyanheads/openstreetmap-mcp-server/issues/29))

## Fixed

- **`openstreetmap_query_raw` surfaces the Overpass parse error from an HTTP 400 response body** instead of a bare status message: the `<strong>Error</strong>: ...`/plain-text `Error: ...` lines Overpass returns are extracted, capped at 300 characters, and appended to the error message; the bare status message is kept when the body carries no recognizable error text. The framework caps a non-ok response body at its first 500 bytes, and the public `overpass-api.de` 400 document puts its parse error past that cutoff, so the extraction stays inert against that specific endpoint until the cap is raised or made configurable upstream ([mcp-ts-core#298](https://github.com/cyanheads/mcp-ts-core/issues/298)); it works today against instances that return a shorter or plain-text error body. ([#33](https://github.com/cyanheads/openstreetmap-mcp-server/issues/33))
