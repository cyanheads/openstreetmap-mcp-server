# 0.3.3 — 2026-07-29

## Changed

- **`openstreetmap_query_bbox`, `openstreetmap_query_nearby`** now surface the Overpass-stated cause of a 5xx response in the error message, via the extractor `openstreetmap_query_raw` already used, shared at `services/overpass/overpass-error.ts`. All three tools also drop the captured non-2xx body from `error.data` once the cause is in the message — it was forwarded as unparsed XHTML under `body` and the legacy `responseBody` alias, duplicating the same document on the wire. ([#46](https://github.com/cyanheads/openstreetmap-mcp-server/issues/46))
- **`openstreetmap_query_bbox`'s `west`/`east` descriptions now state the antimeridian-crossing semantics** — a `west` greater than `east` is a valid box covering `west..180` plus `-180..east`, verified against the default endpoint (a crossing box returns exactly the union of its two non-crossing halves). No behavior changed; the `invalid_bbox` recovery hint was already correct. ([#40](https://github.com/cyanheads/openstreetmap-mcp-server/issues/40))
- **`openstreetmap_search_places`'s `notice` field description now covers the truncation-cap case**, not only the exhausted-paging-walk case — `ctx.enrich.truncated()` writes the cap message into the same key, so a full page of results can carry a notice too. ([#39](https://github.com/cyanheads/openstreetmap-mcp-server/issues/39))

## Fixed

- **`openstreetmap_query_bbox`, `openstreetmap_query_nearby`'s `data_timestamp` no longer falls back to the current wall-clock time** when the Overpass response carries no `osm3s` block — the field is now optional and omitted, matching `openstreetmap_query_raw`'s existing behavior. Previously, two calls over the same cached response could report two different "freshness" times. ([#43](https://github.com/cyanheads/openstreetmap-mcp-server/issues/43))
